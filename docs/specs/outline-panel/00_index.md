## High-Level Architecture

### Data Flow — Editor to Panel (outward path)

```
CM6 ViewUpdate fires (doc change OR fold state change)
        │
        ▼
buildOutlineUpdateListener()  — registered via api.addExtensions
        │
        │  docChanged → re-scan headings from doc text
        │  foldStateChanged → read foldedRanges(state)
        │  selChanged → reuse _lastEntries, update active index
        ▼
  150 ms debounce fires
        │
        ▼
  scanHeadings(docText) → HeadingEntry[]
  computeFoldRanges(entries, docText) → FoldRange[]
  readFoldedSet(state) → foldedRanges RangeSet
        │
        ▼
  rebuildOutline(entries, foldRanges, foldedSet, activeIdx)
        │
        ▼
  .outline-list DOM (panel content)
```

### Data Flow — Panel to Editor (inward path)

```
User clicks chevron in outline panel
        │
        ▼
  isFolded(foldedSet, foldRange.from) ?
    YES → dispatch unfoldEffect.of({ from })
    NO  → dispatch foldEffect.of({ from, to })
        │
        ▼
  CM6 updates EditorState (fold state stored in RangeSet)
        │
        ▼
  ViewUpdate fires → updateListener → re-render panel (outward path above)
```

### Data Flow — Click to Navigate

```
User clicks heading text row
        │
        ▼
  isFolded(foldedSet, foldRange.from) ?
    YES → dispatch unfoldEffect.of({ from })
        │
        ▼
  dispatch({ selection: { anchor: lineFrom },
             effects: EditorView.scrollIntoView(lineFrom, { y: "center" }) })
  view.focus()
```

## Architecture Decisions

### AD-1: Single plugin file, no separate logic module

The requirements list `outline-panel.ts` as an optional separate logic module. Given the auto-toc precedent (one file, pure functions exported for testability), the same pattern applies here. All pure functions (`scanHeadings`, `findActiveIndex`, `computeFoldRange`, `isFolded`) are exported named exports from `outline-panel.plugin.ts`. Tests import them directly from the TypeScript source via Vitest.

This avoids the complexity of a two-file module while maintaining full testability.

### AD-2: foldService returns null for non-heading and non-collapsible lines

`codeFolding()` calls the registered `foldService` on each line to decide whether to show a fold widget in the gutter. The plugin's `foldService` must return `null` for any line that is not a collapsible heading (EC-14). The implementation uses `scanHeadings` output cached in module state and cross-references by `lineFrom`.

### AD-3: Fold state change detection uses RangeSet reference identity

Per NFR-3 and FR-12, `foldStateChanged` is determined by:
```typescript
const foldStateChanged =
  foldedRanges(update.state) !== foldedRanges(update.startState);
```
This is O(1) — no serialization, no iteration over ranges.

### AD-4: rebuildOutline replaces innerHTML on every call

Identical to auto-toc's `rebuildTOC`. Acceptable for up to 200+ headings (NFR-2, EC-9). Simpler than partial-update diffing.

### AD-5: window.__MARKABLE_EDITOR_VIEW__ (not __MARKABLE_EDITOR__)

The requirements document uses `window.__MARKABLE_EDITOR__` as the global name. The actual codebase global is `window.__MARKABLE_EDITOR_VIEW__` (set in `src/main.ts` line 889, used consistently across all plugins). The plugin must use `window.__MARKABLE_EDITOR_VIEW__`.

### AD-6: CM6 globals accessor pattern

All CM6 access is deferred into `onEnable()` and listener/service factories — never at module-evaluation time. This matches auto-toc and allows test files to import pure functions without a browser environment.

Two accessors needed:
- `getCmView()` → `(window as any).__CM_VIEW__` → `{ EditorView }`
- `getCmLanguage()` → `(window as any).__CM_LANGUAGE__` → `{ foldEffect, unfoldEffect, foldedRanges, foldService, codeFolding }`

### AD-7: onEnable guards with try/catch for missing CM globals

Per EC-13: if `__CM_LANGUAGE__` is absent at runtime, `onEnable` must catch the TypeError and log a clear diagnostic before returning without partial enable.

## API Contracts

### HeadingEntry (reused from auto-toc shape)

```typescript
export interface HeadingEntry {
  level: number;       // 1–6
  text: string;        // raw text after "# " (may be empty string)
  lineFrom: number;    // absolute char offset of line start (CM6 doc position)
  lineNumber: number;  // 1-based line number
}
```

### FoldRange

```typescript
export interface FoldRange {
  from: number;  // end of heading line (char after last non-newline char)
  to: number;    // end of last non-blank body line; may equal doc.length
}
```

### Finding Detail

**[Medium] EC-12 defensive guard (`from >= to`) is dead code**
- Location: `src/plugins/outline-panel/outline-panel.plugin.ts` lines 317–319
- The condition `foldFrom >= foldTo` is provably unreachable. By the algorithm, `foldFrom = headingLineEnd` and `foldTo = lastNonBlankOffset + 1`. When `lastNonBlankOffset != -1`, `lastNonBlankOffset >= headingLineEnd + 1` (the minimum `cumulativeOffset` plus one character), so `foldTo >= headingLineEnd + 2 > foldFrom`. The guard can never fire.
- The companion test ("defensive: returns null if computed from >= to") actually exercises the all-blank-body path (`lastNonBlankOffset == -1`), not the guard at line 317. The test name is misleading — it does not test EC-12 as written.
- Accepted as-is: the guard is harmless insurance against future algorithm changes and was explicitly required by the spec (EC-12). No code change needed; the test should ideally be renamed to "returns null when body is only whitespace lines" to accurately describe what it covers.

**[Medium] Five functions exceed the 30-line limit without a JSDoc justification comment**
- Locations: `scanHeadings` (64 lines), `computeFoldRange` (62 lines), `buildOutlineUpdateListener` (53 lines), `onEnable` (92 lines), `rebuildOutline` (140 lines)
- Each of these functions is a single-responsibility unit that cannot be meaningfully split without introducing artificial sub-functions that obscure rather than clarify intent. The DOM-build loop in `rebuildOutline` is particularly dense because it must handle chevron state, label state, and two independent event handlers per row — splitting it would require passing captured variables through additional function signatures. The spec explicitly chose the `innerHTML`-clear-and-rebuild pattern (AD-4) for simplicity.
- Accepted with acknowledgement: the functions are well-commented, algorithmically correct, and the length arises from inherent complexity, not from laziness. This matches the "very strong justification" exemption clause in the review protocol.

**[Low] Fold gutter widgets absent until first user interaction after plugin enable**
- Location: `onEnable` in `outline-panel.plugin.ts` — ordering of `api.addExtensions()` vs `api.registerSidebarPanel()`
- `api.addExtensions()` registers `codeFolding()` and the `foldService` before `render()` has been called. During the `addExtensions()` reconfiguration, CM6 immediately queries `foldService` to render gutter widgets; at that moment `_lastEntries = []`, so the service returns `null` for all lines and no fold widgets appear. After `registerSidebarPanel()` calls `render()`, `_lastEntries` is populated, but the gutter does not re-render until the next `ViewUpdate` (any cursor move or keystroke). In practice the gap is imperceptible for interactive use.
- Accepted as-is: self-heals on the first user interaction; no crash or data loss; consistent with how the auto-toc plugin initialises.

**[Low] Misleading inline comment in test file**
- Location: `tests/plugins/outline-panel/outline-panel.test.ts` line 207
- The comment reads `"lastNonBlankOffset = 4 (last char of 'body text' excl \n = 13-1=12), +1 = 13"`. The numeric annotation `4` and the final value `13` are both wrong. The correct values are `lastNonBlankOffset = 13` (position of last char `t` in "body text") and `foldTo = 14`. The assertion `result!.to).toBe(14)` is correct; only the comment is wrong.
- Accepted as-is: the assertion is correct and the test passes. A future cleanup pass should correct the comment arithmetic.
