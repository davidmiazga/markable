## Problem
Review each plugin against its pack claim and fix failures before any shipping work. Stop after the review list, before the fixes, for a check-in.

Walk every plugin against its pack claim and write down what is wrong. That list is a check-in. Fixes start only after David says to continue. Signing and installers come after those fixes. Do not start a shipping pass while Project, Diary, and the vault row are still wrong.

The phases, in order, are the vault row, the Project board, the Diary calendar, then the plugin review. The review itself stops after the written list of what is wrong, before any fixes. Shipping does not start in the same session as the review.

## In scope
Any code additions need a secondary check - make them part of the workflow. Use repeatable components whenever possible and always follow the styles that are already been set.

## Out of scope
Do not endless repeat tests, mark them done and move on. If it's a complex change, consider adding checks so you can see if things actually pass and are 'good' (not ugly and awkard for the user, streamline whenever possible). DO not introduce new patterns. Do not bother saying you're done without checking - this causes frustration. You need evidence before even considering something done. Even then see if you can improve the experience for the user.

## UX / behavior
Each plugin should behave as expected and be able to be toggled on/off. Plugins that have dependencies should toggle on/off as needed as well. Ensure things are not awkward and streamline the app for as few clicks as possible to get things done.

## Tests
All the usual tests - the app should compile. Also stop and consider any improvements, especially if they are obvious and you have an example of a better pattern from Obsidian or another app.
