## Problem
FeaturesList checklist marks HTML dashboards open.

NOTE ON DASHBOARDS:
1. Dynamic Live Queries vs. Static/Scripted HTML:
   - _folder.md uses select / view blocks (FROM ., WHERE, SORT, LAYOUT cards|table|list|bookshelf) that automatically query the live Vault Index whenever notes are added, renamed, or re-tagged.
   - A pure dashboard.html written by an AI is infinitely more flexible visually (custom charts, KPIs, timelines, custom JS/CSS), but unless it can query the vault at runtime (e.g., via a small window.markable.getVaultIndex() bridge injected into the iframe), its data is a snapshot from when the AI generated it.
2. Markdown Note Composition vs. Full HTML:
   - _folder.md lets you write normal Markdown prose above/below the dashboard block and edit it inline in Typora mode.
   - dashboard.html is best when the entire tab is an app-like view (like CursorModels-10.18.26.html).
3. Coexistence Option:
They don't necessarily have to conflict: a folder could check for _dashboard.html / dashboard.html (or _folder.md), or any .html file in the vault could simply be runnable as an interactive tab with a window.markable read-only bridge so AI-written HTML dashboards can pull live vault notes/tags/frontmatter on the fly.

HTML files in a vault are documents people expect to open and use, the same way they open a note. Markable is part markdown viewer and part browser. A window holds both. A markdown tab is the viewer. An HTML tab is the browser: the page runs, and the host does not reduce it to a static preview. Markable currently answers that open with "Cannot preview this file type," so the file cannot run and cannot see the vault.

The reference page is this repo's project board, `dm-software-machine/board/project-board.html`, built to `.dm-software-machine/board.html`. In a normal browser a person can drag a card between columns, drop a card onto another card to nest it, edit the card's details, type in the search box and the settings fields, switch Kanban and Table, and download Overrides JSON. The page keeps those edits in `localStorage`. It does not write the task store. A vault HTML file opened in a Markable tab, and the same file opened in a second Markable window, must keep that kind of page behavior working. The page may read the live vault. It may not change vault files.

## In scope
- Clicking a `.html` or `.htm` file that sits inside the active vault opens it as an interactive document tab. Today that click opens a media tab that says "Cannot preview this file type."
- The file renders in a sandboxed iframe that fills the tab. Inline and relative scripts run. Buttons, forms, text fields, drag and drop, `localStorage`, and a download the page starts all work inside the page. A host sandbox that blocks any of those fails this ticket. The host installs `window.markable` before the page's own scripts run. The iframe cannot reach the editor DOM or call Tauri commands except through the bridge.
- The same HTML file can open in a new Markable window. That window is also part markdown viewer and part browser: the HTML page fills an HTML tab there, and a markdown link from the page opens a markdown tab in that window. The page's drag, edit, storage, and download behavior is the same in the new window as in the first.
- Relative CSS, JS, and images referenced by that HTML file load. A same-folder or vault-relative link to another `.html` or `.htm` file opens that file as its own interactive tab. A link to a markdown note inside the vault opens that note. An `http:` or `https:` link opens in the system browser. A `javascript:` link, a `file:` link, or a path outside the active vault does not open and does not read the target.
- `window.markable.getVaultIndex()` returns the live vault index for markdown notes: `vaultId`, `builtAt`, `capped`, and `entries` of `path`, `name`, `title`, `tags`, `outboundLinks`, `modified`, `size`. The HTML file does not embed a copy of this data.
- `window.markable.getNote(path)` reads one markdown note inside the active vault and returns `{ path, title, tags, frontmatter, body }`. `frontmatter` is the parsed YAML object, including keys other than `title` and `tags`. The stored index only keeps title and tags, so this read is per note, on demand.
- `window.markable.onVaultChange(listener)` runs the listener after the vault index rebuilds (note added, renamed, retagged, or removed) and returns an unsubscribe function.
- The bridge is read-only. It does not write, rename, delete, or invoke other Tauri commands. `getNote` rejects a path outside the active vault roots and a path that is not markdown, and it does not read that file.
- Opening the same HTML path again activates the existing tab. The tab is part of the saved session and comes back as a running page on the next launch, not as source text and not as the media-preview message.
- Several vault HTML files can be open beside markdown notes. Switching tabs shows the page that belongs to that tab.

## Out of scope
- `_folder.md` select / view blocks, and the cards, table, list, and bookshelf layouts. Clicking a folder still opens `_folder.md` when that file exists.
- Treating `_dashboard.html` or `dashboard.html` as the folder's view. A folder does not gain a new click target in this ticket.
- A query language (`FROM`, `WHERE`, `SORT`) inside the HTML page. The page filters `getVaultIndex()` itself.
- Editing the HTML source in the tab, or writing notes from the bridge. A later ticket can add a write bridge if a page needs to save back into the vault.
- Storing every frontmatter key in the persisted vault index.
- PDF, images, and other non-HTML files.
- A process that is not a Markable window. "Open in New Window" stays inside Markable.
- Rebuilding the project board, or teaching Markable the board's task schema. The board is only the reference page for browser behavior.

## UX / behavior
- The file browser click on a vault `.html` or `.htm` file opens a tab titled with that filename. The page fills the content area. Markable does not add chrome inside the iframe. Dragging, editing fields, switching views, and downloading a file the page creates all happen inside the page and do not change vault files.
- The tab's context menu has "Open in New Window." That opens a Markable window on the same file. Closing the window does not close the tab in the window it came from. Closing the original tab does not close the new window.
- A link inside the page follows the rules in scope: another vault HTML file becomes a tab, a vault note opens in the editor, an external web link leaves the app, and anything outside the vault is ignored. The ignored click does not show a dialog.
- An empty vault returns `entries: []`. A capped index returns `capped: true` with the notes that were indexed. Neither case is an error dialog.
- `getNote` of a missing markdown path inside the vault returns null. `getNote` of a path outside the vault, or of a non-markdown path, rejects and leaves the file unread.
- If the HTML file is missing or cannot be read, the tab stays open and shows "Could not load file." plus the path. No second error dialog.
- An HTML file outside the active vault does not get the bridge and does not open as an interactive tab. It keeps the current "Cannot preview this file type." media message.
- After quit and relaunch, each vault HTML tab that was open is open again and its scripts run with a fresh `window.markable`.

## Tests
- Opening a vault `.html` file creates an interactive tab and does not show "Cannot preview this file type." A button in that page runs its own script.
- A fixture page can drag an element into a drop target, edit a text field, read back a `localStorage` value it wrote, and start a download. Those four actions succeed in a Markable HTML tab and again in a second Markable window opened from that tab. `board.html` is the kind of page this fixture stands in for. It does not have to be copied into the app.
- The iframe document exposes `getVaultIndex`, `getNote`, and `onVaultChange` on `window.markable` before the page script runs.
- `getVaultIndex().entries` includes a markdown note created after the HTML file was saved.
- `getNote` returns a frontmatter key other than `title` and `tags` for a note that has one, and returns that note's body.
- `getNote` rejects a path outside the active vault roots and does not read it.
- `onVaultChange` fires after the vault index reloads, and the unsubscribe function stops further calls.
- A relative link to a second vault HTML file opens that file in a second tab. A link to a vault markdown note opens the note. An `https:` link is handed to the system browser. A path outside the vault does not open and is not read.
- Opening the same HTML path twice leaves one tab. Two different vault HTML files can be open at the same time, and switching tabs shows the matching page.
- Restoring a saved session opens a vault HTML path as a running page with `window.markable`, not as source text and not as "Cannot preview this file type."
- A folder that contains `_folder.md` still opens that markdown file when the folder is clicked.
